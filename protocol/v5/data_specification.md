# R01 — Data-collection and release specification

**Version:** 1.9 draft  
**Date:** October 4, 2026  
**Status:** Working specification for study-team and IRB review; not approved for enrollment or release  
**Controlling design:** [study_overview.md](study_overview.md)

## Purpose and boundary

The first study creates a reusable, documented dataset. It will report recruitment, completion, evidence availability, reviewer agreement, and technical validation; it does not make a formal vaccine-effect or causal claim. A data paper may describe analyses the fields permit without selecting a favorable result. The approved public-use data and documentation will be released regardless of the observed timing pattern. This commitment does not override consent, IRB conditions, or a case-specific disclosure-risk decision. Any subsequent analysis selected after inspection of exposure-linked results must be identified as exploratory.

The rules for collecting, coding, reviewing, counting, suppressing, and releasing records must be frozen before enrollment and versioned if amended. Descriptive plot bins and hypothetical null models are not part of this collection specification. A separate analysis paper must disclose when those choices were made.

## Core measures preserved for later analysis

Use one **ONSET date**: either parent's first notice of the qualifying lasting change. Preserve the original report, later clarifications, each reviewer's assessment, accepted value, corroboration, and precision separately. Earlier illness/uncertainty is timeline context, not another onset endpoint; earliest documented post-change date is a documentation field.

- **Age:** ONSET minus parent-entered birthdate, in days and completed months.
- **A:** ONSET minus the selected most recent actual vaccination date on or before ONSET within 90 days.
- **B:** total complete normal days in that vaccination-to-ONSET window, including disconnected periods, using observed pre-vaccination behavior/skills as baseline. Count vaccination day only if normal throughout; count through the day before ONSET, never ONSET day or pre-vaccination days. Known values satisfy 0 ≤ B ≤ A; A = 0 implies B = 0.
- **C:** ONSET minus the most recent eligible calendar-quarter start or unshifted nominal CDC visit on or before ONSET; nominal visits follow the same 90-day convention.

Without an eligible vaccination anchor, A/B are not applicable, not zero. Keep normal, non-normal, unassessable and unremembered day statuses separate. Preserve exact, approximate, lower-bound, unknown, and baseline-unestablished answers and the supporting timeline. B is directly reported, not derived by subtracting symptom duration from A. Raw B > A discrepancies remain visible and prompt clarification, never silent clamping.

Preserve C values with reference-system and historical schedule identifiers, nominal-age/visit grouping, precision, eligibility, and missing/no-anchor flags. Nominal dates never replace actual administration. Additional fixed-day grids and shifted references are optional later descriptive uses, not additional pre-disclosure prompts or formal tests required in the data paper.

## Data layers and unit of observation

The post-disclosure vaccination-to-ONSET narrative must include the normal periods counted in B, not just notable symptoms/events. Preserve each described period's dates or duration, baseline behavior/skill observations, observer, and normal/non-normal/unassessable/unknown status when available. Retain all disconnected normal periods. Cross-check the directly reported B count against this timeline, recording discrepancies and later clarifications without overwriting raw answers or the locked original narrative. Silence about symptoms does not establish normal functioning. This prompted chronology covers the full vaccination-to-ONSET window even when it exceeds the original unprompted 15-day narrative.

1. **Recruitment-source log:** One row per source and invitation batch, with source code, attempted/delivered/undeliverable counts, batch and reminder dates, confidence group, and stage counts where available. Do not infer that delivery means an invitation was read. Partner identities may be described in the regulatory file but are not embedded in respondent-facing Survey 1.
2. **Survey 1 response:** One row per consenting response about the selected child, including original answers, submission state, eligibility flags, and follow-up permission. Retain nonqualifying and incomplete responses with their dispositions. Contact details are stored separately.
3. **Survey 2 response:** At most one linked response per invited Survey 1 child, with screen-level timestamps and completion/decline/abandonment states. Preserve the original locked A1 narrative, cause-neutral A2–A3 answers, disclosure point, and later prompted answers as distinct fields. Partial responses remain data; blanks after a participant stops are not coded as negative answers.
4. **Evidence inventory:** One row per submitted item, linked to the child through a restricted identifier. Record media type, receipt time, claimed event date, file-created date when available, provenance, content summary, authenticity/legibility concerns, and restricted storage pointer. The source file itself is never public.
5. **Reviewer assessment:** One immutable row per reviewer per child, with completion time, SORA judgment, each date/bound/status, source citation, evidence tier, and conflict flags. Each reviewer locks one assessment without access to the other two judgments. Corrections, if allowed for a clerical error, require a separately logged amendment; the original is not overwritten.
6. **Accepted case table:** One row per child, retaining parent-reported, reviewer-specific, and accepted values separately. A value survives only when at least two reviewers independently choose the exact same value or status; otherwise it is unresolved. Derived intervals are calculated only from the accepted inputs they require. The table carries separate administrative, scientific, evidence, and public-release flags.
7. **Public-use files:** De-identified case and technical-validation tables, a carefully redacted narrative file when safe, a dictionary, flow counts, transformation code, and a release manifest. No contact information, absolute dates, source files, or direct identifiers are released. Restricted originals and the mapping key remain under controlled access.

Stable internal child and evidence identifiers will be randomly assigned; public identifiers will be different and nonreversible without the restricted crosswalk. No respondent name or email may serve as an analysis key. Preserve raw answers and an auditable correction history instead of replacing them with adjudicated values.

## Minimum dictionary and provenance fields

The field-level implementation dictionary will give every variable a name, type, units, allowed values, missing codes, collection screen or source item, transformation rule, and public/restricted disposition. These groups are required:

| Group | Fields and distinctions that must survive |
| --- | --- |
| Funnel | Source and batch codes; invitation and reminder counts; Survey 1 consent/start/submit; screen completion; Survey 2 invite/start/A1 lock/disclosure/continue/explicit decline/abandonment; record request/receipt; payment status. |
| Child and phenotype | Parent-entered birth year and later birthdate; selected-child confirmation; Survey 1 pattern, reported onset age/dateability/records confidence; parent-reported diagnosis; loss/reduction, new behavior, and mixed flags. Parent report is never relabeled as documented diagnosis. |
| Narratives and sequence | Original locked unprompted A1 text/timestamp; cause-neutral A3 uncertain-period and return assessment; prompted full-window chronology; pre-vaccination behavior/skill baseline and dateability; direct total normal-day B count and all supporting normal periods, including disconnected stretches. Preserve symptom timing, maintained/returned/no-return/partial-day sequence status, non-normal versus unassessable/unremembered days, count precision and discrepancies. Symptom resolution and silence do not establish normal functioning; later answers never overwrite A1. |
| Timing | Parent-first-notice ONSET, clarifications and plausible bounds; each reviewer's ONSET assessment, bounds, earliest documented post-change date and unresolved statuses; exact two-of-three accepted values; citations and evidence tiers. Earlier illness and uncertain periods are contextual timeline fields, not another onset date. Preserve skill/behavior observation bounds separately. |
| Visits and products | Parent-reported most recent vaccination within 90 days before ONSET, actual administration date/products when documented, later-vaccination status, prior-visit spacing, vaccine-free regular well visit, no-visit status, lifetime vaccination report, 90-day history-completeness status, and disagreement flags. A scheduled dose is not an administered dose. |
| Evidence and review | Item type, provenance, content/date support, record usability, reviewer citations, agreement class (3/3, 2/3, unresolved), and reasons for unresolved judgments. An after-only item can establish a documented post-change observation without proving the first onset day. |
| Derived variables | Age in days/completed months at accepted ONSET; A from the eligible vaccination; directly reported B, count precision and sequence/timeline support; C for calendar-quarter/nominal CDC anchors with rule version, eligibility/no-anchor and missing-input flags; ONSET and vaccination weekday where exact dates permit. Visit-to-ONSET lag for vaccine-free well visits and vaccination-to-documentation lag are separately labeled; neither changes ONSET or supplies A/B in no-vaccination cases. |
| Release | Consent version and data-sharing permission, public-use eligibility, narrative publication/suppression decision, case-row publication/suppression decision, reason category, redaction version, and reviewer signoff. These flags must not depend on the direction or strength of a timing result. |

Use explicit missing/status values: **not asked due to branch**, **not reached because of partial response**, **answered unknown**, **not supplied**, **submitted but unusable**, **reviewers unresolved**, **not applicable**, and **withheld from public release**. Do not combine these with a substantive No or zero. Exact codes and data types are implementation items to finalize with R03 and R06 before enrollment.

## Fixed construction rules

- **Agreed Q2 — complete normal days only:** B counts calendar days at the observed pre-vaccination behavior/skill baseline throughout the day, judged from ordinary parental observations, not continuous surveillance. Preserve partial-day return status, approximate dates/duration, and uncertainty separately; do not add fractions or round into B. A definite non-normal part prevents classification as a complete normal day; an unassessable part alone does not establish abnormality. B = 0 does not imply no brief return. A normal period spanning only parts of two calendar days is not a complete calendar day; retain it as timeline context.
- **Agreed Q1 — incomplete day classification:** When A and the pre-vaccination baseline are established, preserve N = definitely complete normal days, D = definitely not complete normal days, and U = unknown/unassessable days within the same A-day window. Keep inability to assess and inability to remember as separate reasons within U. Reconciled counts satisfy N + D + U = A; raw inconsistencies remain visible and require clarification, not forced arithmetic. If U = 0 and counts are otherwise exact, B = N is exact. If U > 0, N is only a lower bound for B, with possible range N through N + U; unknown days are not abnormal days. Preserve the direct parent count separately from any reconciled count/bounds and their provenance. Approximate dates/counts retain approximate status; no applicable anchor or unestablished baseline does not produce a numeric zero. Lower-bound B values do not enter exact-count histogram bins as if exact.
- Preserve normal-period dates/durations, observed baseline behavior/skills and observers throughout the vaccination-to-ONSET window, alongside non-normal, unassessable and unknown periods. Vaccination itself is not an observed abnormality. Keep observations separate from attributed causes and reconcile the direct B answer with the narrative without overwriting raw responses.
- B adds all complete normal days within the selected vaccination-to-ONSET window, including disconnected normal periods. Exclude ONSET day and pre-vaccination days; include vaccination day only if normal throughout. Known values obey 0 ≤ B ≤ A. Preserve raw out-of-range counts and clarification history; do not clamp them. Keep zero, unknown, lower bounds and baseline-unestablished distinct; lower bounds are not exact histogram entries. No eligible vaccination anchor means A/B not applicable.
- Survey 1 invitation eligibility and the 6–24-completed-month detailed cohort are governed by the overview and final instruments. Preserve screened eligibility separately from the later age calculated from the parent-entered birthdate and reviewer-agreed ONSET. Never revise the administrative 100-record count because of a later scientific judgment.
- The 100-submission administrative flag requires the Survey 1 screen, required Survey 2 fields, and an apparently in-window vaccination or vaccine-free regularly scheduled well-visit document, as specified in the overview. It is separate from full-payment eligibility, final scientific usability, public-release status, and later analysis inclusion. All submissions from open batches are retained even after 100 are reached.
- ONSET defines the actual 90-calendar-day visit lookback. Link at most one eligible visit to a case: the most recent documented administered vaccination on or before ONSET within that window; only if no such vaccination occurred, the most recent qualifying vaccine-free regular well visit, provided the 90-day vaccination history is sufficiently established. Otherwise code no qualifying/confirmed anchor and retain the case. A parent-reported or uncertain most-recent visit remains visible but must not be represented as confirmed.
- Derive A only from accepted ONSET and its eligible actual vaccination date; day 0 means dates coincide. Retain earlier illnesses or uncertain periods separately without converting them into negative-onset lags. Never replace an unresolved ONSET with vaccination, a nominal reference, or the first dated post-change observation.
- Preserve parent report, each locked reviewer answer, accepted answer, evidence tier, and uncertainty bounds separately. Do not average nonmatching dates or require a visit anchor to retain a child's phenotype and timing data. Unresolved/missing-date cases remain in counts and in any analysis for which their available fields suffice.
- Treat parent-reported never-vaccinated, parent-reported no vaccination in 90 days, record-supported vaccine-free-at-visit, and sufficiently established vaccine-free 90-day history as distinct states. The narrow record request does not verify a complete lifetime or 90-day history merely by obtaining one visit record.

R02 will state exact inclusion flags for each eventual descriptive subset; R06 will define evidence tiers and date-corroboration thresholds. Those rules must be agreed before review or outcome-linked analysis. This document does not create a new requirement for parents to submit full vaccination histories.

## Public release and suppression rule

The working public-use file includes consented, safely de-identified child-level responses, derived ages and intervals, quality/provenance flags, and redacted unprompted narratives, including eligible partial responses. Restricted source files and contact details are never public. Each proposed public row and narrative will undergo documented disclosure-risk review under the eventual R07 procedure; removing names and dates alone is not assumed sufficient for a rare, richly described case.

**If an individual narrative cannot be made safe for open release without unacceptable identification risk, retain the unredacted original in the restricted dataset and withhold that narrative from the public file.** The public file will carry a narrative-suppressed flag and a nonrevealing reason category where even that row is safe to publish. If the remaining child-level row is itself unsafe, withhold the row as well; publish only aggregate counts of suppressed rows and narratives at a safe level of detail. Never substitute a fabricated narrative or silently drop a case from study totals. Apply the same risk criteria without regard to exposure history or timing pattern. Document the decision, approver, and redaction version in the restricted audit trail. Controlled re-review remains possible only through approved access.

Consent and IRB approval must permit the intended public and controlled-access uses; a record is not made public merely because it is retained. Before release, check combinations of derived ages, intervals, product labels, narrative details, rare clinical events, and recruitment-source information for linkage risk. The final R07 plan will define who conducts the review, the repository, access terms, suppression thresholds, and a correction/withdrawal process for an accidental disclosure. A copy of the proposed public files must pass this review before posting.

## Processing, validation, and release package

Build the public-use dataset from immutable raw exports and locked reviews with a versioned script. The script must (1) validate respondent and item links, screen sequence, date ranges, and branch status; (2) calculate administrative and scientific flags without reading or optimizing any outcome histogram; (3) apply the exact two-of-three agreement rule; (4) derive ages and lags with documented day-zero and completed-month conventions; (5) produce a row-level discrepancy report and funnel counts; (6) remove restricted columns, apply approved narrative redactions/suppressions, and scan public outputs for prohibited identifiers; and (7) produce checksums, a dictionary, code version, and a release manifest. Test the pipeline on fictitious edge cases before enrollment and rerun it at each release.

Technical validation in the data paper should report stage denominators, missingness by field and source, evidence availability/tiers, three-reviewer agreement and unresolved rates, visit-anchor provenance, date consistency, and public suppression counts. It may also give examples of downstream uses of the fields, clearly separated from any later hypothesis analysis. A release is never conditioned on whether observed lags look favorable, unfavorable, or uninformative.
